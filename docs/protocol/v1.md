# Huddly Realtime Protocol Specification — v1

> **Status:** Finalized (ARCH-010) · **Protocol Version:** `1` · **Target Milestone:** M0–M7

The Huddly protocol defines the transport, envelope, catalog, authorization rules, conflict resolution, clock synchronization, REST surface, error registry, and versioning for realtime synchronization across all Huddly clients (browser extension, web client, and future mobile apps).

> **Architectural Invariant:** The protocol is strictly client-agnostic. It **must never reference browser-extension APIs** (`chrome.*`, `browser.*`, tabs, webRequest). Mobile, desktop, web, and extension clients speak the exact same protocol.

---

## 1. Event Envelope

Every realtime message sent across the control and data plane (over WebSocket) is wrapped in the standard `EventEnvelope`.

### 1.1 Envelope Structure

```json
{
  "protocolVersion": 1,
  "eventId": "3f2504e0-4f89-41d3-9a0c-0305e82c3301",
  "eventType": "PLAYBACK_PLAY",
  "roomId": "9c858901-8a57-4791-81fe-4c455b099bc9",
  "actorId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "revision": 42,
  "serverTimestamp": 1786780000000,
  "payload": {
    "mediaId": "media-video-1",
    "position": 105.32,
    "playbackRate": 1.0
  }
}
```

### 1.2 Field Definitions & Authority

| Field             | Type                      | Set By                    | Description                                                                                                                                                          |
| ----------------- | ------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `protocolVersion` | `integer`                 | Client / Server           | Identifies the protocol contract version. Current version is `1`. Messages with unsupported versions are rejected.                                                   |
| `eventId`         | `string (UUIDv4)`         | Sender (Client or Server) | Unique identifier for the individual message. Used for idempotent processing and client-side deduplication.                                                          |
| `eventType`       | `string (Enum)`           | Sender                    | Identifies the domain event and dictates the schema of the `payload`.                                                                                                |
| `roomId`          | `string (UUIDv4)`         | Sender                    | Identifies the target room context.                                                                                                                                  |
| `actorId`         | `string (UUIDv4) \| null` | Server                    | User ID of the participant who triggered the event. Always set/verified by the server from the authenticated session. `null` for server-originated lifecycle events. |
| `revision`        | `integer (>= 0)`          | Server                    | Monotonically increasing state sequence number per room. Server is the sole authority for assigning revisions; client values in requests are ignored/overwritten.    |
| `serverTimestamp` | `integer (epoch ms)`      | Server                    | Authoritative server clock timestamp when the event was processed. Client-submitted timestamps are never trusted.                                                    |
| `payload`         | `object`                  | Sender                    | Strongly-typed event payload conforming to the event schema for `eventType`.                                                                                         |

## 3. Server Authorization Rules

> **Zero Trust Security Principle:** **Never trust a client claiming to be host or possessing elevated privileges.** The server validates every inbound event against authenticated session state, room membership, and verified role permissions before committing mutations or broadcasting to other participants.

### 3.1 Validation Pipeline

For every inbound message received from a WebSocket client:

1. **Authentication Check:** Server resolves the user/session from the established WebSocket handshake connection context. Unauthenticated connections are closed immediately with `AUTH_INVALID_TOKEN`.
2. **Room Membership Verification:** Server queries active room members. If the actor is not an active member of `roomId`, the request is rejected with `ROOM_MEMBER_NOT_FOUND`.
3. **Role & Permission Matrix:**
   - **`PLAYBACK_*` & `MEDIA_*`:** Only members with the `HOST` role (or delegated playback control) are permitted to alter playback state. If a `PARTICIPANT` attempts a `PLAYBACK_PLAY` command, the server rejects it with `ROOM_ROLE_INSUFFICIENT` and issues no room broadcast.
   - **`MESSAGE_CREATED` & `TYPING`:** Allowed for any active room member whose status is not muted.
   - **`MESSAGE_DELETED`:** Allowed if `actorId == message.senderId` OR `actor.role == HOST`.
   - **`ROOM_CLOSED`:** Allowed only if `actor.role == HOST`.
4. **Envelope Rewriting:** The server **overwrites** `actorId`, `serverTimestamp`, and `revision` before persistence and broadcast. Any client-provided timestamp or revision is discarded.

## 4. Conflict Resolution & Ordering

Huddly utilizes a **Server-Authoritative State Machine** to guarantee total event ordering and deterministic client state:

1. **Monotonic Revision Sequence:** The server maintains a strictly increasing `revision` integer per room. Each validated state transition increments `revision = revision + 1`.
2. **Server Ordering Resolves Race Conditions:** If two clients issue conflicting actions simultaneously (e.g., Host presses `PLAY` while another controller presses `PAUSE` at the same physical millisecond), the server processes them sequentially in the order received by the room lock queue. The first processed mutation increments revision $N$; the subsequent mutation increments revision $N+1$.
3. **Client State Rule (`shouldApply`):**
   $$\text{apply}(E) \iff E.\text{revision} > \text{currentRevision}$$
   Clients accept only events that advance the local revision counter. Stale, duplicate, or out-of-order events from network delays are discarded without side effects.
4. **Clients Never Decide Final State:** A client optimistically renders local UI feedback, but must immediately conform to the server-broadcast state if a divergence occurs.

## 5. Clock Synchronization & Drift Calculation

Because participant devices have differing system clocks, all time-dependent calculations rely on server clock estimation.

### 5.1 Clock Sync Protocol (NTP Ping / Pong)

Clients periodically (every 10–30 seconds) execute a lightweight clock sync exchange:

1. Client records local timestamp $t_0$ and transmits `SYNC_PING { clientSendTime: t0 }`.
2. Server receives ping at server timestamp $t_1$, immediately responds with `SYNC_PONG { clientSendTime: t0, serverReceiveTime: t1, serverTransmitTime: t2 }`.
3. Client receives pong at local timestamp $t_3$.

$$\text{roundTripTime (RTT)} = (t_3 - t_0) - (t_2 - t_1)$$

$$\text{clockOffset} = \frac{(t_1 - t_0) + (t_2 - t_3)}{2}$$

$$\text{serverNow} = \text{localNow}() + \text{clockOffset}$$

Clients maintain a rolling window of recent RTT and offset measurements (using median filtering) to filter out transient network jitter.

### 5.2 Expected Playback Position & Drift Correction

Given a playback state snapshot with base `position` (in seconds), `serverTimestamp` (epoch ms), `playbackRate`, and `playing`:

$$\text{expectedPosition} = \begin{cases} \text{position} + (\text{serverNow} - \text{serverTimestamp}) \times \frac{\text{playbackRate}}{1000}, & \text{if } \text{playing} = \text{true} \\ \text{position}, & \text{if } \text{playing} = \text{false} \end{cases}$$

$$\text{drift} = (\text{localVideo.currentTime} - \text{expectedPosition}) \times 1000 \quad (\text{ms})$$

Clients calculate the absolute drift magnitude $|\text{drift}|$ and apply the four-tiered correction model implemented in `@huddly/sync-engine` (`DEFAULT_THRESHOLDS`):

| Action           | Threshold                                    | Strategy               | Behavior                                                                                                      |
| :--------------- | :------------------------------------------- | :--------------------- | :------------------------------------------------------------------------------------------------------------ |
| **`none`**       | `abs(drift) < 50ms` (`ignoreMs`)             | Imperceptible buffer   | In-sync. Zero correction applied.                                                                             |
| **`nudge-rate`** | `50ms <= abs(drift) < 200ms` (`nudgeMs`)     | Smooth rate adjustment | Adjust `playbackRate` by +/-5% (clamped to `[0.25, 4.0]`) while playing until aligned.                        |
| **`soft-seek`**  | `200ms <= abs(drift) < 500ms` (`softSeekMs`) | Gentle seek            | Seek directly to `expectedPosition` for moderate drift where rate-nudging would take too long to converge.    |
| **`hard-seek`**  | `abs(drift) >= 500ms`                        | Immediate hard seek    | Force seek directly to `expectedPosition` (e.g. for large timeline jumps, buffer underruns, or late joiners). |

> **Note on Acceptance Targets vs. Correction Thresholds**:
> The "< 200ms" sync requirement in `MVP.md` is an **end-to-end acceptance target / SLA** for user-perceived synchronization across the entire system, NOT a single correction threshold. The numeric coincidence with `nudgeMs` (200ms) has caused confusion in earlier drafts. Under the active model, rate-nudging operates below 200ms to maintain this target seamlessly, while deviations >= 200ms escalate to seeks to rapidly restore sync.

| `ROOM_FULL`              | `409`       | Room has reached maximum participant capacity (MVP capacity: 10).      |
| `ROOM_LOCKED`            | `403`       | Room is locked by the host; new joins are prohibited.                  |
| `ROOM_CLOSED`            | `410`       | Room has been terminated by the host or expired.                       |

## 8. Versioning & Evolution Strategy

The protocol is strictly versioned via the top-level `protocolVersion` integer.

### 8.1 Backward Compatibility Rules

1. **Additive Changes (Minor Evolution):**
   - Adding optional fields to event payloads is backward-compatible.
   - Introducing new `eventType` values that older clients can safely ignore is backward-compatible.
   - Older clients MUST ignore unrecognized fields in payload objects.
2. **Breaking Changes (`protocolVersion` Increment):**
   - Renaming or deleting any field in `EventEnvelope`.
   - Modifying data types of existing fields in `EventEnvelope` or existing event payloads.
   - Changing the semantic behavior or state machine progression of existing `eventType` transitions.
   - Changing clock sync or drift formulas in a manner incompatible with older clients.

### 8.2 Handshake & Version Negotiation

During WebSocket handshake initialization:

- Client supplies its supported `protocolVersion` in connection headers/query parameter:
  `GET /ws/v1?protocolVersion=1&token=...`
- If server does not support the requested `protocolVersion`, the connection is closed with status code `4400` and error code `PROTOCOL_VERSION_UNSUPPORTED`.
